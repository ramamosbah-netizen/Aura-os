# A1.1 CLM Design Gate — Contracts

Status: `APPROVED — BOUNDED IMPLEMENTATION IN PROGRESS`

The current Contracts clause surface is a reusable library. It is not yet a
contract-specific drafting and negotiation authority. This gate defines the
decisions required before adding that capability; it intentionally adds no
schema, API, workflow, sharing endpoint, or customer portal.

## Required separation

```text
Clause Library
  → Contract Clause Snapshot
  → Contract Revision R01…Rn
  → Internal Review
  → Client Review / controlled share
  → Negotiation
  → Approval
  → Signed immutable revision
  → Post-sign Amendment / Variation through C6 authority
```

The standard clause library remains reusable source material. A contract gets a
snapshot at the time a clause is added; later library edits must not rewrite that
snapshot. A signed revision is immutable.

## Decisions required before implementation

| Area | Decision that must be explicit |
|---|---|
| Revision identity | Revision number/ID, parent revision, author, timestamp, reason, diff model and immutable snapshot format. |
| Revision states | Draft, internal review, client review, negotiated, approved and signed states, including legal transitions and replay behavior. |
| Terms model | Which payment, retention, warranty, duration, milestone and special-condition fields are structured versus document text. |
| Clause association | How library clauses are copied into a contract revision and how special clauses are authored without mutating the library. |
| Negotiation | Comment/change-request ownership, visibility, resolution, and whether negotiation is pre-sign only. |
| Client sharing | Controlled PDF/document source, recipients, method, expiry/revocation, share audit, and whether email/link delivery is in scope. |
| Approval | Internal approval authority, segregation of duties, approval evidence and relationship to the existing signing authority. |
| Signing | Which approved revision is signed and frozen; no direct edits after signing. |
| Post-sign changes | Amendment/addendum/variation boundary and explicit ownership by the existing C6 change-control authority. |
| Documents | Whether the existing Documents authority stores generated/shareable revisions and evidence. |
| External access | Whether customer access is limited to controlled documents now; portal/authentication is a separate decision. |
| Permissions | Capability permissions for draft, review, share, approve and sign; no role-name checks in domain code. |
| Audit/events | Required actor, tenant, revision, action, timestamp, correlation and share provenance; replay dedupe. |
| Tenant/security | Cross-tenant isolation, link access policy, expiry and revocation requirements. |
| Financial effect | Confirmation that pre-sign terms do not mutate signed commercial facts; post-sign effects use approved change authority. |

## Non-goals of this gate

- No mutation of the standard clause library to represent negotiation.
- No generic Contract status PATCH as a drafting substitute.
- No direct edits to a signed revision.
- No second variation/amendment authority in Contracts.
- No customer portal or unauthenticated share links without security approval.
- No invented legal semantics for termination, liability, LD, renewals or amendments.

## Required approval artifact

Before implementation, approve a bounded contract covering the decisions above
and identify the minimum lifecycle/API/persistence/UI slice. If a decision is not
required for the first slice, mark it explicitly deferred rather than silently
implementing it.

The design decision has now been approved. The first implementation boundary is
the contract-specific revision/snapshot spine: revisions are tenant-scoped,
lineage-preserving and persisted separately from the reusable clause library;
signed revisions are immutable. Controlled sharing, customer portal access,
post-sign amendments/renewals and full approval/SoD policy remain dependent on
their existing platform authorities and are not fabricated by this slice.

## A1.1 implementation evidence (additive)

- `ContractRevision` is the pre-sign content authority. It carries a stable id,
  contract id, revision number, parent revision, reason, structured terms and
  clause snapshots plus actor/timestamp metadata.
- The revision transition matrix is explicit (`draft` → review/negotiation →
  approved → signed). Terminal signed rows are immutable and repeated states
  are idempotent. A revision addressed through a different contract URL is
  rejected.
- The API exposes tenant-scoped list/create/status-transition routes and the Web
  BFF forwards authenticated and replay-safety headers. Contract 360 exposes an
  Agreement & revisions view with draft creation, review/negotiation/approval/
  signing actions and immutable signed-state readback.
- Migration `0276_contract_clm_revisions.sql` adds the tenant-isolated revision
  store with a unique `(tenant_id, contract_id, revision_number)` constraint.
  It has not been claimed as disposable-PostgreSQL proof in this report.

The implementation is therefore not a claim that every CLM capability in the
approved target is complete. External client sharing, clause-library picker and
contract-specific snapshot authoring UI, comparison, document delivery,
approval/SoD policy, history aggregation and post-sign amendment/renewal remain
explicit completion items where repository authority is not yet available.
