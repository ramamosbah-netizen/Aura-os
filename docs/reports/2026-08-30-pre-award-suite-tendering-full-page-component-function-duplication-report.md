# Pre-Award Suite / Tendering — Full Page, Component, Function and Duplication Report

**Audit date:** 30 August 2026
**Environment:** Local AURA OS on `main` (`http://localhost:3000`)
**Primary pages checked live:** `/suites/pre-award`, `/tendering`, `/tendering/outcomes`
**Scope:** Suite discovery, canonical Tendering pages, visible functions, component ownership, reporting coverage, navigation duplication, workflow correctness, backend capability exposure, and remediation priorities.

## Executive summary

`/suites/pre-award` and `/tendering` are not two versions of the same page.

- `/suites/pre-award` is the **generic suite catalogue page**. It shows the suite description, one discovered function, four static capability claims, and an **Open suite** link.
- `/tendering` is the **canonical Pre-Award operational dashboard**. It shows live KPIs, an attention queue, an AURA brief, and six workflow shortcuts.
- The Pre-Award domain has **six canonical Tendering page routes**, plus the generic suite catalogue page.
- The suite catalogue advertises **1 available function**, while the dashboard advertises **6 shortcuts**. This is source-of-truth drift, not a true capability shortage.
- `/tendering/outcomes` is the current report page, but it is a small summary: five KPIs, the latest 12 outcomes, and loss-reason counts. It has no filters, paging, saved views, charts, competitor analysis, CSV/Excel, or print/PDF.
- The backend already provides more reporting depth than the UI uses, including paged outcomes and competitor head-to-head analytics.
- Duplication is concentrated in navigation metadata, TypeScript interfaces, money formatting, KPI presentation, and page-local styling. The authoritative Tendering domain data is not materially duplicated.
- Two workflow defects need priority attention:
  - the visible **Won** button calls the generic status route, but the backend explicitly forbids setting `won` there and requires the governed award-evidence route;
  - the visible **Submit** button also calls the generic status route. The service correctly creates a minimal submission record, but the UI never collects the richer method, portal, reference, addenda acknowledgement, validity, notes, and actor facts accepted by the dedicated submit route.

## What each requested page actually does

### `/suites/pre-award`

The suite catalogue is generated by one reusable `SuiteHome` component for every AURA suite. For Pre-Award it currently renders:

- breadcrumb back to Suites;
- suite name and lifecycle description;
- **Open suite** link to `/tendering`;
- **Available functions** with only `Tenders`;
- four static capability labels, all marked `IMPLEMENTED`.

It does not load Tendering KPIs, attention, outcome analytics, report content, tender rows, or pricing data.

The one-function result comes from `suiteFunctions()` in `apps/web/lib/suites.ts`. That function filters `ALL_ITEMS` from `components/nav.ts` by route ownership and de-duplicates by `href`. Only `/tendering/tenders` is currently present in `ALL_ITEMS`, so Pricing and Outcomes never appear here.

### `/tendering`

The canonical dashboard loads tenders and outcome analytics concurrently and composes them through the reusable `SuiteDashboardShell`.

Visible functions:

1. Tenders
2. BOQ
3. Estimation & Pricing
4. Submissions
5. Clarifications
6. Outcomes & Reports

It also provides:

- active tender count;
- total active bid value;
- in-progress count;
- win rate and won/lost count;
- lifecycle attention ordered by tender value;
- an AURA brief;
- continue-working context;
- explicit ownership guidance.

The dashboard is the correct canonical home. The suite catalogue should link to it and describe its functions; it should not duplicate the dashboard's operational logic.

## Duplication and drift analysis

### 1. Two function catalogues

Pre-Award functions are defined in two unrelated places:

- `components/pre-award-dashboard.tsx` defines six `SHORTCUTS`;
- `components/nav.ts` exposes only the Tender register to `ALL_ITEMS`, which `suiteFunctions()` uses for `/suites/pre-award`.

Result: the two pages disagree, and future changes can drift again.

### 2. Multiple labels share one destination

BOQ, Submissions and Clarifications all route to `/tendering/tenders` because they are tender-scoped capabilities. This is conceptually valid, but `suiteFunctions()` de-duplicates only by URL. A URL-based catalogue cannot preserve distinct workflow labels that intentionally open the same parent register.

The function model needs a stable function ID separate from `href`.

### 3. Navigation taxonomy still places Tenders under Delivery

The legacy navigation model lists `Tenders` inside the `Delivery` group, while `AURA_SUITES` correctly assigns all `/tendering/*` routes to Pre-Award. Permissions happen to share the same `suite.dealChain` gate, but the information architecture has two names for the same ownership boundary.

### 4. Tender type definitions are repeated

Local `Tender` interfaces are independently declared in:

- `components/pre-award-dashboard.tsx`;
- `app/tendering/tenders/page.tsx`;
- `components/tenders-client.tsx`;
- `app/tendering/tenders/[id]/page.tsx`;
- `app/tendering/tenders/[id]/pricing/page.tsx`;
- `components/tender-pricing-client.tsx`.

The fields and status unions can drift. A shared web contract or generated SDK type should be the canonical source.

### 5. Pricing summary types are repeated

`SheetSummary` exists separately in the Tender register page, its client component, and the Pricing summary page. This should be one exported contract.

### 6. Currency formatting is repeated and inconsistent

At least four page/component-local AED formatters exist. They vary in rounding, fraction digits, locale selection, and zero rendering. The same bid value can therefore be displayed differently between dashboard, register, pricing and outcomes.

### 7. KPI cards are reimplemented

The dashboard uses the shared `SuiteMetric` contract, while the Tender register and Outcomes page each define local `Kpi` components and local inline styles. A shared report metric/card primitive would reduce visual and behavioral drift.

### 8. Report tables are reimplemented

The Outcomes page uses a basic table and the Tender register uses another hand-built table even though `AuraDataTable` already supports search, sorting, facets, pagination, saved URL state, mobile cards and column visibility.

### 9. Page-local inline styles dominate Tendering

The register, detail, pricing summary and Outcomes page each carry separate inline-style maps. This makes spacing, typography, responsive behavior, status colors and print behavior harder to normalize.

### 10. Read failures can look like empty business data

`getJson()` returns `null` for forbidden, server-error, unreachable and malformed-response cases. The dashboard and report pages sometimes distinguish a total outage, but partial failures can still render dashes or empty states that look factual. Management reporting should use `fetchJson()` and preserve the reason a read failed.

## Priority findings

### P0 — The visible Won action cannot complete the governed workflow

`TendersClient` sends `PATCH /api/tendering/tenders/[id]/status` with `status: "won"`. The Tendering controller explicitly rejects `won` through that route. A valid win must use `POST /tendering/tenders/[id]/award` and capture awarded value, currency, award date, optional reference/document, and the authenticated actor.

**Impact:** the visible action either fails or encourages bypassing the award evidence required to drive contract creation and opportunity closure correctly.

**Required change:** replace the button with an award-evidence dialog wired through a web BFF route to the governed award endpoint. Do not copy the current status mutation into a report component.

### P1 — Submission captures only a minimal record

The visible Submit button sends the same generic status PATCH. The service safely routes `status: "submitted"` through `submit()`, so status, event and a minimal TenderSubmission record remain atomic. However, the web action does not collect or pass the submission method, portal, reference, submitted time, acknowledged addenda, validity, notes, or authenticated actor fields accepted by `POST /tendering/tenders/[id]/submit`.

**Impact:** the status is valid, but submission history and operational reporting contain placeholder/null channel and provenance details.

**Required change:** introduce a submission form and use the authoritative submit command. Show submission history on Tender 360.

### P1 — The suite catalogue hides five of six functions

The catalogue shows only Tenders because it derives functions from a legacy navigation list rather than the dashboard's workflow descriptors.

**Impact:** discoverability is poor and capability truth contradicts the visible function list.

**Required change:** create one `PRE_AWARD_FUNCTIONS` registry with stable IDs, labels, descriptions, icons, destinations and availability. Render it in both the suite catalogue and dashboard.

### P1 — Outcomes is not yet a full report page

The report hard-caps the view to 12 rows, while the non-paged backend list itself caps at 100. There is no search, result/date/client/owner/source filter, sorting, pagination, export, print, saved view, trend chart or drill-down.

**Required change:** make `/tendering/outcomes` the canonical full Pre-Award report center rather than adding a duplicate report under `/suites/pre-award`.

### P1 — Competitor intelligence is computed but discarded

The domain analytics returns `byCompetitor` with encounters, wins, competitor wins and win rate against each competitor. The page's local `Analytics` interface omits this field, so the UI cannot render it.

**Required change:** expose a competitor table/chart and include it in filtered exports.

### P1 — Capability truth is static and overstates usable completeness

All four catalogue capabilities are marked `IMPLEMENTED`, even though the web submission path is incomplete, the visible win action is invalid, and reporting is basic.

**Required change:** separate backend capability, usable UI, governance completion and verification evidence. Until the command paths are corrected, `Submissions & Outcomes` should not be presented as unqualified complete.

### P2 — Large component and local-type debt

`TenderDetail` is roughly 1,448 lines and embeds qualification and clarification applications. Domain types and formatters are repeated throughout the suite.

**Required change:** extract domain panels and shared contracts without creating new stores or duplicated business rules.

## Recommended full report page

Keep `/suites/pre-award` as a lightweight catalogue. Expand `/tendering/outcomes` into the canonical **Pre-Award Reports** page.

### Report sections

1. **Executive summary**
   - active tender count and value;
   - submitted count and value;
   - decided, won and lost;
   - win rate by count and value;
   - average bid value and average margin;
   - due/overdue tender exposure.

2. **Outcome trends**
   - won/lost count by month;
   - won/lost value by month;
   - win rate by source, account, owner and value band;
   - pricing margin versus outcome.

3. **Competitor intelligence**
   - encounters;
   - wins against;
   - losses to;
   - win rate against;
   - winning competitor and bid value where recorded.

4. **Loss analysis**
   - ranked loss reasons;
   - value lost by reason;
   - trend over time;
   - missing-debrief completeness indicator.

5. **Paged outcome register**
   - tender, account, source, owner, result, bid value, competitor, reason and decision date;
   - search, date range, result, source, owner, customer and competitor filters;
   - sorting, column visibility, pagination and row drill-down.

6. **Exports**
   - filtered CSV;
   - Excel workbook;
   - print/save-as-PDF management pack;
   - scope, filters, tenant and generated-at timestamp printed on every output.

### Recommended component composition

| Component | Role |
|---|---|
| `PreAwardReportsPage` | Server boundary, permission/error-aware reads |
| `PreAwardReportsClient` | Filter state, report composition and URL synchronization |
| `ReportMetricGrid` | Shared KPI cards |
| `AuraDataTable` | Paged/filterable outcome register |
| `BarChart` / `BarList` / `Donut` | Trends, reasons and competitor analysis |
| `ExportButton` | CSV, Excel and print/PDF |
| `SaveViewButton` | Saved filter/report views |
| `ReportScopeBar` | Tenant, date window, active filters and freshness |

Do not duplicate outcome aggregation in the browser. Filtered aggregates should come from one report query/endpoint or from the same authoritative filtered result set used by the register.

## Recommended single source of truth

Introduce a function descriptor independent of navigation URL:

```ts
interface SuiteFunctionDefinition {
  id: string;
  suiteId: string;
  label: string;
  description: string;
  href: string;
  capabilityId: string;
  availability: 'implemented' | 'partial' | 'missing' | 'unverified';
}
```

For Pre-Award, define six records once and consume them in:

- `/suites/pre-award`;
- `/tendering` shortcuts;
- command/search navigation;
- capability verification tests;
- role/function visibility.

The stable `id` allows BOQ, Submissions and Clarifications to remain distinct functions even when they share the Tender register destination.

## Implementation sequence

### Phase 0 — Correct governed actions

1. Add web BFF routes for tender submit and award.
2. Replace generic Submit with a structured submission dialog that calls the dedicated submit route.
3. Replace generic Won with an award-evidence dialog.
4. Connect Lost to a required/optional debrief policy and outcome record.
5. Add action-level regression tests.

### Phase 1 — Remove navigation drift

1. Create the shared Pre-Award function registry.
2. Render the registry in both catalogue and dashboard.
3. Remove Tendering ownership from the legacy Delivery navigation group.
4. Add tests asserting the six Pre-Award functions are visible in both surfaces.

### Phase 2 — Build the full report page

1. Replace page-local outcome rendering with `PreAwardReportsClient`.
2. Use the paged outcome endpoint.
3. Add filters and URL-persisted state.
4. Render competitor analytics and trend charts.
5. Add filtered CSV, Excel and print/PDF.
6. Add report scope and freshness metadata.

### Phase 3 — Consolidate components and contracts

1. Export shared Tender, SheetSummary and Outcome contracts or consume generated SDK types.
2. Centralize AED/date formatters.
3. Extract Qualification and Clarifications from `TenderDetail`.
4. Move report/register tables to `AuraDataTable`.
5. Replace repeated KPI implementations with a shared report metric primitive.

## Acceptance criteria

- `/suites/pre-award` and `/tendering` show the same six function labels from one registry.
- Function identity is not lost when several functions share `/tendering/tenders`.
- The visible Submit action creates a TenderSubmission record with actor and submission facts.
- The visible Won action captures award evidence and uses the governed award endpoint.
- Outcomes can be filtered by date and result, searched, sorted and paged beyond 100 records.
- Competitor head-to-head analytics are visible.
- CSV, Excel and print/PDF reflect the full filtered result, not only the visible page.
- Report outputs show tenant, date window, active filters and generated time.
- Forbidden, unreachable and server-error states cannot render as a factual empty report.
- Shared contracts replace repeated Tender and SheetSummary interfaces.
- Automated tests cover route ownership, function parity, submit/award commands, report filtering, paging and exports.
- The report remains usable on narrow/mobile layouts and supports keyboard/screen-reader navigation.

## Conclusion

Pre-Award already has a strong operational core: tender registration, bid scoring, BOQ management, rate build-up, pricing, quotation generation, clarifications and outcome analytics. The main weakness is not missing domain logic. It is the gap between **what exists**, **what the two entry pages advertise**, and **which governed paths the visible buttons actually use**.

The correct direction is to keep `/tendering` as the operational home, keep `/suites/pre-award` as a catalogue, and make `/tendering/outcomes` the single full report center. Navigation descriptors, report components and contracts should be consolidated, while authoritative submission, award and outcome logic remains in Tendering rather than being copied into new UI code.
