# TC-08 / TC-09 / TC-11 — the approved checklist, built and assessed

2026-09-25. Built against design commit `e61ea730` and the programme owner's approval of it (four
decisions, five conditions). Proven against the running API with auth on, PostgreSQL migrated to
0388, and the shipped roles — `u-e2e-qaqc` and `u-e2e-qaqc2` (QA/QC), `u-e2e-tc` (commissioning
engineer). **Nothing is promoted.** Every acceptance proof for these three rows asks for "an approved
checklist of every supported system", and whether that is met is a decision for the owner, set out at
the end.

## What changed

**Quality owns the checklist.** A tenant *System Template Library* — one versioned template per
canonical `ELV_SYSTEMS` id (never `other`) — starts empty and proposes no point for any system. A
published template is frozen; a change is its next version. Quality *adopts* a published template into
a project as that project's revision 1, adapts it, submits it, and a **different** QA/QC person
approves it (`quality.itp.approve`, and the preparer is refused in the service and by a CHECK
constraint). Approval freezes everything — system, points, criteria, mandatory flags, revision. A
change is the next revision; approving it supersedes the previous one in the same transaction.

**T&C executes it.** A commissioning record is created *from* the approved revision (or bound to it
later, explicitly, by a person holding `commissioning.record.checklist-binding`). Its points arrive
from the revision carrying their lineage (`origin = itp`, code, mandatory flag); a hand-typed point on a
bound record is refused. A binding is pinned for good: a later revision or template version applies to
records bound afterwards, and the record executing revision 1 stays on it after revision 2 is approved.

**PASS is the approved revision's.** A system is commissioned only when bound, every **mandatory**
point of its revision has a latest run of pass, no point of any origin stands failed, and no defect is
open. An optional point may stay unexecuted. The service, the workspace, the readiness chain (a new
`checklist` gate owned by Quality) and PostgreSQL all ask the same question in the same words, so the
screen cannot promise what the backend refuses. The fail → defect → correction → retest loop and the
per-point run history are unchanged.

**Installation inspection is untouched.** The existing ITP stays `kind = installation_inspection` —
no system, no revision, its WBS release gates as before — and is filtered out of every commissioning
read; its page lists installation plans only.

**Existing records.** Nothing already commissioned is re-judged (it reads as history). A record in
progress stays unbound until a person binds it, and cannot be commissioned until then.

## Defects found on the way, and fixed

1. **An upsert is not a new row (my own first cut).** The stores save with
   `INSERT … ON CONFLICT DO UPDATE`, and PostgreSQL fires BEFORE INSERT row triggers for the proposed
   row before it detects the conflict. Judged as inserts, every save of a record was a fresh binding —
   so a record pinned to a revision since superseded could never be saved again — and every sign-off
   was "written commissioned". The SQL tests used hand-written UPDATEs and could not see it; the live
   trace did. The guards now step aside for a row that exists and let the UPDATE branch judge it, and
   two tests go through `PostgresCommissioningStore` itself. Migration 0388 was rolled down and
   re-applied from the corrected file.
2. **`GET /quality/itps` ignored `?projectId=`** (pre-existing). The guard authorised a project
   member FOR the project and the handler answered with every plan in the tenant: a member of one
   project read every other project's ITPs, and a project's checklist screen showed another project's
   approved revision as its own. The real browser caught it. The list now narrows to the project.
3. **The T&C register form offered `pa_va`** (pre-existing), which is not a canonical id and is stored
   as `other` — a system no checklist can ever be approved for. The form now lists `ELV_SYSTEMS`.
4. **A revision's document number carried its revision** (`ITP-X-R1` on revision 2). A number names
   the checklist, not one revision of it; the revision is carried on its own.

## Assessment — each row against the eight frozen layers

Each row's acceptance proof: *"Repeat for an approved checklist of every supported system with
representative roles, persisted evidence and controlled output"* (TC-08, TC-11) and *"Each supported
system executes its approved points with original failure and retest retained"* (TC-09).

**TC-09 — Retest history.** domain, persistence, api, ui, browser: proven here (run lineage retained
through binding, retest and sign-off, under shipped roles). permissions: proven for the checklist acts;
the run append's own denial is proven by `commissioning-permissions.spec.ts`. actualOutput: the
retest is an audit event (`commissioning.test-run.recorded`, `isRetest`) — proven in the service, not
read back from the persisted event store here. handoff: the history reaches the handover dossier
through the existing TC-GATE-7 path, not re-proven for a bound record. **Closest to complete.**

**TC-08 — Defect and corrective action.** domain, persistence, api, ui, browser: proven here (a
defect raised from the failing point blocks PASS until closed with its resolution). permissions: T&C
proven; the Design / Technical Engineer the row names has no modelled part in corrective action.
actualOutput: no controlled output of the defect and its correction beyond the persisted record —
the certificate is TC-10's slice. handoff: escalation to Quality by NCR reference exists and was
re-run in regression, not re-proven as a receipt. **Two layers open.**

**TC-11 — Readiness rollup.** domain, api, ui: proven (the checklist gate, per-project coverage with
whose move it is). persistence: derived and never stored, read from persisted evidence; the PASS rule
it reports is held by PostgreSQL. permissions: the workspace read's denial is proven (a viewer is
refused 403); the coverage read's is not asserted. browser: coverage and the binding state proven; the
readiness section's checklist gate is not asserted by name in the browser. actualOutput and handoff:
the rollup feeds handover submission through the existing gate; not re-proven here. **Four layers
open.**

TC-10 (controlled certificate) is untouched and stays in its DocControl slice. The certificate does not
yet print which checklist revision the system was commissioned against.

## For the owner to decide

**What "every supported system" means.** The contract forbids inventing technical checklists, so
the library is empty until Quality writes one per system. Two readings, with different effects:

- **A — the mechanism is per canonical system.** Binding, PASS and coverage are keyed on the
  canonical id and behave identically for every one of the 23 systems; proof on representative
  systems (intercom in the browser, access control live, CCTV, structured cabling, nurse call and
  public address in tests) stands for all, and coverage shows every other system as not ready.
  *Effect:* TC-09 can be promoted once its handoff and output layers are accepted as above; TC-08 and
  TC-11 still have open layers.
- **B — the capability needs an approved checklist for each system in a tenant.** That is Quality's
  content, not code. *Effect:* none of the three can be completed by engineering; they close when
  Quality has approved checklists for every system a tenant supports.

**Accepted limits** (built as the approval bounded them): moving a record that is already executing to
a newer revision is a separate governed act that does not exist; nothing notifies the second QA/QC
person that a revision is waiting for approval (the approver finds it on the checklist screen, not in
My Work); a template can be retired but not withdrawn from a project that adopted it.

## Owner decisions (received) and TC-09 closed

The owner chose **interpretation A**: the governed mechanism must behave identically for every
canonical `ELV_SYSTEMS` id, with representative end-to-end proofs and complete per-system coverage;
no checklist content is invented, and a system stays NOT READY until Quality has published its
template and independently approved the project revision. TC-08, TC-09 and TC-11 were each to close
their open layers before promotion.

**TC-09 — COMPLETE (38/180).** The two open layers, closed:

- **actualOutput — the persisted audit history, read back.** A governed route
  (`GET /commissioning/records/:id/history`) reads the record's events back from the PostgreSQL event
  store: the binding (now also recorded when a record is *created* from the revision — before this, a
  record's history started at its first run with nothing saying what it was tested against), every run
  with `isRetest` and who recorded it, the sign-off. The system's page shows it; the evidence pack now
  names the approved revision and prints each run of a retested point
  (`#1 fail (No image — Cable fault at camera end) → #2 pass`).
- **handoff — received in the handover dossier.** The dossier's line for a system carries
  `tested against ITP-CCTV rev 1 · passed on retest: IMG-01`; it is captured into the issued manifest as
  it stood at issue, and Handover/FM (`u-e2e-fm`) reads it there.
- **permissions.** T&C and QA/QC read the history; a viewer without a commissioning grant is refused 403.
- **Interpretation A.** PostgreSQL binds, refuses PASS until the mandatory point passes, and commissions
  for all 23 canonical systems identically; the domain carries each of the 23 through template →
  publish → revision → independent approval; `other` is refused even as a draft.

Proof: `retest-history-handover.spec.ts` (shipped `u-e2e-tc`, `u-e2e-qaqc`/`u-e2e-qaqc2`, `u-e2e-fm`,
viewer denial), `approved-checklist.pg.test.ts` 20, commissioning 237 and quality 82 unit tests, the
dossier / evidence pack / lineage browser specs re-run green, turbo test/typecheck/lint 78/78.

**Finding for the owner — nobody operational can submit a handover that carries a controlled
document.** Submitting a package opens a document-control transmittal, and since Wave C an
authorisation failure there is not swallowed (a document leaving the business must be recorded). The
transmittal asserts `doccontrol.transmittal.create`. Of the shipped roles, PM and T&C hold
`commissioning.handover.submit` but not the transmittal; the Document Controller holds the transmittal
but not submit; only the administrator holds both. So any package whose dossier cites an O&M manual or
an as-built — the ordinary case — can be submitted only by an administrator. In the TC-09 proof the
administrator submits, and the receipt under test is Handover/FM's. No role was widened. The options
(grant the delivery roles the transmittal; let submission open the draft transmittal under the handover's
own authority with the release still Document Control's; or record the issue unconveyed and put it in
Document Control's queue) are an authority decision.
